# Continuous training from GitHub

NaNLM should not treat GitHub as a live training dependency. It should treat
GitHub as a **river of provenance-pinned code** that is periodically distilled
into immutable, content-addressed memory generations. The runtime never calls
GitHub. The repository holds the contract; shards hold the observations;
`.nan` images hold the brain.

The loop is:

```
GitHub / local repos
  -> pin commits
  -> license + secret + generated-code filters
  -> normalize + chunk
  -> chunk manifest (hashes, provenance, language)
  -> runner ring leases jobs
  -> additive count shards
  -> merge (commutative addition)
  -> compile typed slot memory
  -> evaluate candidate generation
  -> publish/rollback immutable generation
  -> runtime uses base + selected deltas
```

The supplied plumbing gate is:

```sh
make continuous-check
```

It ingests a deliberately adversarial local fixture, rejects a minified file,
a generated file, and a secret-bearing file, builds two shards, proves
`A+B == B+A` byte-for-byte, compiles the merged counts to typed slot memory,
runs it on `nanlm_vm`, and exercises a four-runner ring with one failed runner.

This is a **provenance and merge gate**, not a quality claim. The fixture is
tiny. It proves the pipes are connected and deterministic.

## 1. Why this shape fits NaNLM

The model is a counting memory, not a gradient-trained transformer. That gives
the continuous loop three unusual properties:

1. **A contribution is a shard, not a checkpoint.** A runner can process one
   repository, one language pack, or one time window and upload a small
   additive shard.
2. **Merge is exact and order-independent.** `sum(A,B) = sum(B,A)`. No optimizer
   state, no floating-point drift, no all-reduce.
3. **Forgetting is a policy, not a side effect.** New counts can be added
   without destroying old counts. If a new domain should dominate, use a
   separate delta generation and route to it; do not overwrite the base.

That last point is the key to using a constantly training layer "as a whole":
the system can keep a stable general memory and add narrow, reversible experts.

## 2. Supply: from repository to chunk manifest

### 2.1 Pin, then fetch

Never train the moving default branch silently. The ingestion manifest records:

- repository identity;
- exact commit SHA;
- source URL;
- file path;
- license identifier;
- file hash and chunk hash;
- language tag;
- byte range;
- normalized text location.

`tools/nanlm_ingest.py` supports local repositories and pinned GitHub tarballs:

```sh
python3 tools/nanlm_ingest.py \
  --github shemshallah/NaNLM@<commit> \
  --out build/ingest

python3 tools/nanlm_ingest.py \
  --repo data/code_fixture \
  --out build/ingest \
  --concat build/corpus.txt \
  --include-docs
```

A production crawler should be a separate service with a durable allowlist of
repositories and a queue of `(repo, commit)` pairs. GitHub Actions is a good
**trigger**, but a poor crawler: scheduled workflows are jittery and have a
small storage budget.

### 2.2 License gate

Default allowlist: MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, MPL-2.0,
Unlicense, CC0-1.0, 0BSD. Copyleft and unknown-license repositories are skipped
unless explicitly enabled. The per-file SPDX header overrides the repository
license; a file that claims a disallowed license is rejected even inside an
allowed repository.

This is a conservative engineering default, not legal advice. A production
system needs a license policy reviewed per jurisdiction and per model release.

### 2.3 Quality gate

Reject:

- binaries and non-UTF-8 files;
- minified files and source maps;
- generated files (`DO NOT EDIT`, `@generated`, `generated by`);
- vendored/dependency trees (`node_modules`, `vendor`, `third_party`, ...);
- lockfiles;
- files with secrets (private keys, AWS keys, GitHub tokens, common API keys);
- oversized files;
- hidden directories.

Normalize only BOM and line endings. Do not reformat code: indentation, line
breaks, and comments are signal.

### 2.4 Chunking

Chunks are large enough to preserve local structure and small enough for a
runner lease. The default is 64 KiB, split on newline boundaries. A production
version should record and preserve a small overlap for cross-chunk context, or
build shards over a repository file rather than per chunk. The current shard is
3-byte context, so a one-byte boundary loss is small but not zero.

### 2.5 Deduplication

Deduplicate by normalized chunk hash, not by path. The same code appears in
forks, vendored copies, generated clients, and tutorials. A production manifest
should carry a `canonical_chunk_sha256` and a `duplicate_of` pointer so the
merge job can choose one copy without losing provenance.

## 3. Training: shard algebra

### 3.1 Raw self-supervised shard

A raw shard counts:

```
(context 3 bytes, next byte) -> count
```

`nanlm_shard build` emits it. `nanlm_shard merge` folds shards by integer
addition, saturating at 65535. The shard is content-addressed by its bytes.

### 3.2 Teacher shard

A teacher shard counts:

```
(context 8 bytes, next byte) -> weight
```

A teacher emits top-k bytes per context. The current typed slot memory uses the
last three bytes, so 8-byte teacher records are aggregated down to 3-byte
contexts. The 8-slot student will consume the full 8-byte context instead.

### 3.3 Compile

```sh
nanlm_shard build CORPUS OUT [START END]
nanlm_shard merge MERGED A.shard B.shard ...
nanlm_shard_slot --shard MERGED --corpus CORPUS \
  --out model.nas --expected model.expected --manifest model.manifest
nanlm_asm model.nas model.nan
nanlm_vm --img model.nan --steps ...
```

`make shard-slot-check` proves that the shard path and the direct corpus path
produce **byte-identical** `.nas` files on the same training range. That is the
core continuous-training invariant.

### 3.4 Time windows and decay

Counts are additive and do not decay. That is good for reproducibility, but it
means old code dominates forever unless policy changes. The clean solution is
**generation separation**, not destructive overwrite:

- `base` generation: broad, slow-moving;
- `window-2026-11` generation: recent code;
- `lang-rust` generation: language expert;
- `repo-<hash>` generation: a single repository's style.

A later extension can attach an `epoch` or `weight` to shards and compile
time-weighted counts. Do not silently rewrite historical counts.

## 4. Runner ring

### 4.1 Ring contract

A ring is `N` logical runner slots. Each slot has:

- `runner_id`;
- `generation`;
- `manifest_sha256`;
- current lease;
- heartbeat/expiry;
- output shard hashes;
- failure count.

Work is grouped into deterministic jobs from manifest chunks. A job id is
`j-00000`, and its initial ring position is `H(job_id) mod N`. The **successor**
is `(position + 1) mod N`. If a runner dies or misses its lease, the successor
inherits the job. No global lock is required for assignment; the lease table is
the authority.

`tools/nanlm_ring.py` implements the control-plane core:

```sh
python3 tools/nanlm_ring.py plan --manifest build/ingest/manifest.jsonl \
  --runners 8 --chunks-per-job 8 --out ring/plan.json
python3 tools/nanlm_ring.py simulate --plan ring/plan.json \
  --fail 1 --out ring/run.json
python3 tools/nanlm_ring.py materialize --plan ring/plan.json --out ring/jobs
python3 tools/nanlm_ring.py verify --plan ring/plan.json --shards ring/shards
```

Production state belongs in reporam, not a laptop JSON file. The plan is a
derived, reproducible artifact; the lease/attempt journal is the mutable state.

### 4.2 Why a ring

A ring gives simple, deterministic failover and locality:

- deterministic assignment makes retries cheap;
- successor failover avoids a central scheduler hot spot;
- each job's output is content-addressed, so duplicate execution is harmless;
- runners can be phones, Actions jobs, or GPU workers;
- a slow runner can be skipped by advancing its lease, not by rebalancing
  every shard.

### 4.3 Leases

A lease contains `(job_id, runner_id, expires_at, attempt, manifest_hash)`.
Workers renew only while active. A reaper expires stale leases and reassigns to
the successor. Duplicate completion is accepted only if the shard hash matches
the manifest's expected work hash; otherwise the job is quarantined.

### 4.4 Replication and quorum

A shard is published only after:

1. the runner hashes the output;
2. a second runner or verifier recomputes a sample;
3. the merge job can read it from at least two independent mirrors.

The ring should not trust a single runner's bytes. Counts are cheap to verify:
recompute a subset of records and compare.

### 4.5 GitHub Actions as ring v0

A scheduled workflow can:

- resolve new pinned commits;
- cache/restore the shard index;
- fan out a matrix of runner slots;
- build shards;
- upload artifacts;
- run one merge job and publish a candidate generation.

This is enough for early volunteer scale. It is not enough for continuous,
low-latency training: Actions jobs are ephemeral and GitHub artifacts are not a
database. The eventual ring should be long-lived runners backed by R2/S3 or a
RAM/GPU farm, with GitHub as the manifest and review layer.

## 5. The constantly training layer

### 5.1 Two layers, not one monolith

```
stable base generation G0
  + delta generation D1 (recent code)
  + delta generation D2 (language expert)
  + delta generation D3 (task/teacher)
  -> router / mixture
```

Each generation is immutable. A delta can be small: it only stores prototypes
for contexts it observed. The runtime can query the base and the selected
deltas, then combine their next-byte distributions.

### 5.2 Memory algebra

For a context `c`, each generation `g` returns a count vector `counts_g[c][b]`.
The mixture is:

```
p(b | c) = normalize( sum_g w_g(c) * (counts_g[c][b] + alpha * unigram_g[b]) )
```

Where `w_g(c)` is the router weight. For a language-specific delta, `w_g` is
high when the current file extension or recent bytes match that language; for
the base, `w_g` is the fallback. Because counts are additive, a merged
generation is exactly the same as querying the union of its parts when the
weights are equal. This is the "use it as a whole" property.

### 5.3 Router

A first router can be tiny and interpretable:

- file extension / language tag;
- last path separator and extension bytes in the context;
- repository id hash bucket;
- confidence from the base (if base is uncertain, allow the delta to speak);
- explicit task tags (`code`, `shell`, `sql`, `docs`).

A later router can be a learned LUT/regime gate. The router must be evaluated
separately from the memory: a better memory with a bad router can look worse.

### 5.4 Promotion and compaction

Deltas are not promoted just because they are new. A candidate generation is
published only if:

- its shard set is complete and hash-verified;
- it beats the base on the held-out code card;
- it does not regress the general/English card beyond a tolerance;
- it improves at least one declared slice (language, task, or repository type);
- it is reproducible from the manifest;
- a human or CI has approved the model card.

Periodically compact a set of deltas into a new base. Compaction is just a
merge of count shards plus a rebuild of prototypes. Keep the old generation and
its manifest for rollback.

### 5.5 What "constantly" means

Not "mutate the live model on every request." That is unsafe, unreproducible,
and invites poisoning. Instead:

- **continuous ingestion** of pinned code;
- **continuous shard production** by the ring;
- **periodic candidate generations** (hourly/daily/weekly);
- **fast promotion** for narrow deltas;
- **instant rollback** by generation pointer;
- **canary traffic** before full promotion.

The model can learn every hour while the served brain stays a named,
evaluated generation.

## 6. Evaluation: code is not Alice

A code model needs code-specific cards:

### 6.1 Splits

- **repo-holdout**: train on repositories A..Y, evaluate on repository Z. This
  tests generalization to a new codebase.
- **time-holdout**: train on commits before T, evaluate on T..now. This tests
  whether the model learns durable structure or memorizes a snapshot.
- **language-holdout**: train without Rust, evaluate on Rust. This tests
  cross-language byte structure.
- **file-holdout**: hold out entire files, not random bytes. Random bytes leak
  the file's style into the training set.
- **contamination check**: normalize whitespace/comments and check for exact
  n-gram overlap with the evaluation set.

### 6.2 Metrics

- next-byte top-1 and top-5;
- bits per byte;
- bracket/indentation continuation accuracy;
- identifier continuation;
- per-language and per-file-size buckets;
- step count and bytes per query on `nanlm_vm`;
- cold/warm latency for paged memory.

### 6.3 Baselines and controls

Always report:

- interpolated byte n-gram;
- raw slot memory;
- typed slot memory;
- teacher-distilled memory;
- fixed-order vs routed context;
- random labels / random router controls.

A generation is not "better" because it is bigger. It must beat a matched
baseline at the same inference budget.

## 7. Security and provenance

A public code river is also an adversarial input channel.

- **Poisoning**: an attacker can add comments or code that steer a context.
  Mitigate with repository allowlists, shard review, per-repo caps, duplicate
  detection, and canary evaluations.
- **Secrets**: reject files that look like credentials; never ingest `.env`,
  key material, or private repositories without explicit policy.
- **License laundering**: record the exact commit, path, and detected license;
  make the manifest auditable; allow takedown by removing a shard and rebuilding.
- **Supply-chain**: pin commits and tarball hashes; verify runner outputs;
  sign release manifests.
- **Data retention**: GitHub content can change or disappear. The manifest and
  shard hashes are the durable record; mirrors serve the bytes.

## 8. Scale and cost

The first bottleneck is not GPU compute; it is **manifest and shard hygiene**.

- Raw counting is cheap and parallel.
- Teacher inference is the expensive part; cache teacher shards by
  `(model, tokenizer, commit, chunk_hash)`.
- Deduplicate before teacher inference.
- Prefer per-language shards so a language expert can be promoted without
  rebuilding the base.
- Keep the hot set small; stream cold prototypes from repovram.
- A 1 GB corpus is ~2.4 GB of raw 3-gram records before dedupe; plan storage
  accordingly.
- The 8-slot student multiplies prototype width and inference cost; use it for
  teacher contexts that actually carry 4–8 bytes of signal, not by default.

## 9. Roadmap

### Phase A — plumbing (now)

- `nanlm_ingest.py` with license/secret/generated/minified gates.
- deterministic chunk manifest.
- shard → typed slot compile, exact corpus equivalence.
- ring plan/failover/materialize prototype.
- CI gate on a fixture.

### Phase B — real code supply

- crawler allowlist + commit queue;
- repo/time/language holdouts;
- content-addressed shard store outside git;
- GitHub Actions matrix as ring v0;
- code eval card.

### Phase C — teacher and 8-slot student

- Qwen/byte-level teacher on runner ring;
- 8-byte context student (8 byte + ctype slots);
- teacher shards cached by model+chunk;
- promotion gate against n-gram and 3-byte student.

### Phase D — continuous memory service

- base + delta generations;
- language/task router;
- lease/merge service backed by R2/S3;
- canary promotion and rollback;
- live observability and poison quarantine.

## 10. Honest status

What exists and passes:

- ingestion with license and security filters;
- deterministic chunks and manifest;
- additive shards and exact merge;
- shard → typed slot → `.nas` → VM;
- exact corpus-vs-shard compile equality;
- a ring planner with failover and materialized jobs.

What does not exist yet:

- a real GitHub crawler at scale;
- a real Qwen teacher run in this environment;
- the 8-slot student;
- a multi-generation runtime router;
- a production shard store;
- a code-quality win over the n-gram.

The next honest milestone is not "train on all of GitHub." It is:

> **One pinned repository, one held-out file, one teacher, one candidate
> generation, one honest code card.**

That is small enough to reproduce and large enough to tell us whether the
continuous architecture is learning anything real.
